# 제품 및 화면 명세

문서 버전: 1.0 | 작성일: 2026-10-12 | 상태: 구현 전 개발 기준안

이 패키지는 실행 가능한 앱이 아니라 Codex가 앱을 구현하기 위한 명세다. 아래에서 `확정`은 사용자가 직접 지정한 내용이며, `기본안`은 구현을 시작하기 위해 정한 변경 가능한 제품 결정이다.

## 1. 제품 정의

**한 줄 설명:** 나만의 요리법을 공유하고, 서로 만들어 본 후기를 나누며, 매달 좋은 레시피를 함께 선정하는 커뮤니티.

**핵심 흐름:** 레시피 등록 → 다른 사람의 요리와 사진 후기 → 질문과 개선 의견 → 월간 평가 → 수상과 명예의전당 → 다음 레시피 등록.

| 구분 | 결정 |
|---|---|
| 확정 | 다른 사이트 레시피를 모아 평가하는 서비스가 아니라, 사용자가 직접 작성하는 레시피 커뮤니티 |
| 확정 | 웹 우선, Next.js, Supabase, npm |
| 확정 | 의견 교환, 평점, 이달의 레시피와 명예 수상 |
| 검토한 수익 방향 | 식재료 및 조리도구 제휴, 브랜드 후원 대회 |
| 기본안 | 한국어, 한국 시간 기준 월간 운영, 모바일 우선 반응형 웹 |
| 기본안 | 가칭 `레시피 어워즈`, 저장소 이름 `recipe-community` |
| 기본안 | 이메일 회원가입으로 시작하고 소셜 로그인은 후속 확장 |
| 기본안 | 초기에는 상금 없이 금상, 은상, 동상 배지와 수상 기록 제공 |
| 기본안 | 회원의 레시피 공개 등록과 어워즈 출품은 별도 행동 |

서비스명, 도메인, 브랜드 컬러는 변경 가능하다. 이름의 상표 사용 가능성을 확인했다는 뜻은 아니다.

### 초기 사용자와 검증 가설

초기 콘텐츠 테마는 자취 요리, 간단한 집밥, 가성비 한 끼로 시작한다. 데이터 모델과 카테고리는 다른 요리도 수용한다. 특정 테마를 전체 서비스의 영구 제한으로 만들지 않는다.

검증할 가설은 세 가지다. 작성자는 자신의 레시피를 다른 사람이 만들어 준다는 반응 때문에 다시 등록한다. 독자는 실제 조리 사진과 구체적인 후기가 있는 레시피를 저장하고 사용한다. 월간 행사는 첫 방문이 아닌 반복 참여의 이유가 된다. 이 가설은 실측 전에는 성과나 시장 사실로 표현하지 않는다.

### 현재 구현하지 않는 것

독립 자유게시판, 실시간 채팅, DM, 팔로우 피드, 동영상 업로드, 모바일 앱, 다국어 UI, AI 레시피 생성, 자동 영양 분석, 외부 레시피 수집, 쇼핑몰, 장바구니 결제, 정기 구독, 상금 자동 지급, 크리에이터 수익 정산, 밀키트 제조와 배송은 범위 밖이다.

의견 교환은 레시피 상세 댓글에서 먼저 검증한다. 팔로우나 별도 게시판을 추가하지 않았다는 이유로 핵심 커뮤니티가 미완성인 것은 아니다. 반대로 가입 화면과 카드 UI만 만든 상태를 서비스 완료로 보지 않는다.

| 정상 회원 | 본인 레시피 작성, 타인 레시피 후기, 댓글, 북마크, 출품, 신고 |
| 이용 제한 회원 | 공개 열람과 본인 계정 처리만 허용. 신규 쓰기와 평가 불가 |

관리자 역할은 사용자가 수정할 수 있는 프로필이나 인증 메타데이터에서 읽지 않는다. 관리자는 첫 베타의 일반 어워즈에 출품하거나 점수를 보탤 수 없다. 개발용 계정과 fixture도 실제 수상 집계에서 제외한다.

## 4. 핵심 사용자 시나리오

### 4.1 레시피 작성

회원이 `레시피 쓰기`를 누르면 서버에 초안 식별자를 먼저 만든다. 기본 정보, 재료, 조리 단계, 사진을 입력하고 수동 저장 또는 지연 자동 저장한다. 저장 상태를 `저장 중`, `저장됨`, `저장 실패`로 구분한다. 실패했는데 페이지를 닫아도 된다고 안내하지 않는다.

발행 전에는 입력 검증, 이미지 처리 완료, 콘텐츠 작성 권한 확인, 공개 범위 안내를 통과해야 한다. 발행은 DB 트랜잭션으로 새 불변 버전을 만들고 현재 공개 버전 포인터를 교체한다. 외부 스토리지 처리는 발행 트랜잭션에 섞지 않는다.

레시피는 기본적으로 공개다. 초안만 비공개이며 팔로워 공개 같은 복잡한 공개 범위는 제공하지 않는다.

### 4.2 요리 후기

독자는 레시피를 만든 뒤 사진 1~3장, 별점 1~5, 구체적인 후기를 제출한다. 어떤 레시피 버전을 보고 만들었는지 서버가 기록한다. 사진만으로 조리 사실이 입증되지는 않으므로 화면 용어는 `요리 사진 후기` 또는 `사진 첨부 후기`를 사용한다.

같은 사용자는 같은 레시피 버전에 후기 하나를 보유한다. 다시 제출하면 기존 후기 편집으로 안내한다. 레시피 작성자는 자신의 레시피에 후기나 평점을 남길 수 없지만 댓글로 설명할 수 있다.

### 4.3 의견 교환

댓글 유형은 `질문`, `대체 재료`, `개선 제안`, `일반 의견`이다. 별점 없이 텍스트만 등록할 수 있고, 답글은 한 단계까지만 허용한다. 작성자 답글에 `레시피 작성자` 표시를 붙인다. 댓글의 공감 수를 어워즈 점수로 사용하지 않는다. 초기에는 공감 버튼 자체도 제외한다.

### 4.4 월간 어워즈

작성자가 행사 규칙을 보고 자신의 적격 레시피를 출품한다. 출품한 버전이 고정되고, 평가 기간에 등록된 적격 요리 후기만 해당 행사에 반영된다. 종료 후 관리자는 신고와 후보 점수를 검토한 뒤 확정한다. 상세 규칙의 단일 기준은 `03_AWARDS_AND_REVENUE.md`다.

## 6. 화면 명세

### 홈

상단에는 로고, 레시피 탐색, 이달의 어워즈, 명예의전당, 검색, 레시피 쓰기, 계정 메뉴를 배치한다. 모바일은 탐색, 어워즈, 쓰기, 내 공간을 하단 내비게이션으로 제공하되 키보드와 안전 영역을 가리지 않는다.

본문 순서는 짧은 서비스 소개와 대표 행동 버튼, 현재 어워즈, 최근 요리 후기가 달린 레시피, 새 레시피, 지난달 수상작이다. 첫 화면을 거대한 홍보 배너로 채우지 않는다. 현재 행사가 없으면 `첫 어워즈를 준비하고 있어요`를 보여 주고 가짜 마감 시간을 만들지 않는다.

### 탐색

검색 대상은 제목과 재료 이름이다. 기본 정렬은 최신순이며 `평점순`, `후기 많은 순`, `저장 많은 순`을 추가한다. 평점순은 평균과 후기 수를 보정한 점수 기준임을 설명한다. 후기 0개는 0점이 아니라 `후기 없음`으로 표시한다.

필터는 카테고리, 최대 총 소요 시간, 난이도다. MVP 카테고리는 `밥/덮밥`, `면`, `국/찌개`, `반찬`, `고기/생선`, `샐러드`, `간식/디저트`, `음료`, `기타`로 시작한다. 카테고리와 검색용 태그는 서로 다르다.

검색 상태는 `q`, `category`, `maxMinutes`, `difficulty`, `sort`, `page`에 저장한다. 페이지당 기본 12개, 최대 24개다. 무한 스크롤보다 페이지 이동을 먼저 구현한다. 허용되지 않은 정렬 값은 최신순으로 정규화한다.

### 레시피 카드

완성 사진, 제목, 작성자, 총 소요 시간, 난이도, 현재 버전의 평균 평점과 후기 수, 북마크 버튼을 표시한다. 수상 배지는 행사 이름과 월을 포함한다. 과거 버전의 수상이라면 `v1 수상`처럼 범위를 명시한다.

가격 추정, 영양 수치, AI 추천 점수는 데이터가 없으면 표시하지 않는다. 카드 전체 링크 안에 북마크 버튼을 중첩해 접근성 문제를 만들지 않는다.

### 레시피 상세

대표 사진과 제목 다음에 작성자, 발행/수정 시점, 현재 버전, 요약, 분량과 소요 시간을 배치한다. 이어서 재료, 조리 단계, 작성 팁, 요리 후기, 의견 교환을 제공한다. 데스크톱에는 재료와 저장 버튼을 보조 열로 고정할 수 있지만 모바일은 본문 흐름을 우선한다.

`1인분/2인분/4인분` 변경은 명시적인 숫자 수량만 비례 계산한다. `약간`, `한 줌`, `취향껏`은 자동 변환하지 않는다. 단위 환산은 하지 않는다. 인분 변경으로 가열 시간이나 안전한 조리 시간이 비례 변경된다고 안내하지 않는다.

발행 버전이 바뀌면 이전 후기에는 `이전 버전으로 만든 후기`를 표시한다. 현재 버전 평점과 이전 버전 평점을 섞어 하나의 점수로 표시하지 않는다. 특정 출품 버전을 열었을 때 최신 버전으로 자동 이동시키지 않는다.

### 작성과 편집

큰 단계는 `기본 정보 → 재료 → 조리 단계 → 미리보기`다. UI는 하나의 폼 안에서 구성해도 된다. 별도 마법사 라이브러리는 필요하지 않다.

| 입력 | 발행 기준 |
|---|---|
| 제목 | 공백 정리 후 5~80자 |
| 소개 | 20~500자 |
| 인분 | 정수 1~20 |
| 준비 시간 | 0~720분 |
| 조리 시간 | 0~720분, 준비+조리 1~1,440분 |
| 난이도 | easy / medium / hard |
| 카테고리 | 활성 카테고리 하나 |
| 재료 | 1~40행, 이름 1~50자, 수량은 숫자 또는 수량 설명 |
| 조리 단계 | 1~20개, 단계 설명 10~1,500자 |
| 완성 사진 | 처리 완료된 사진 정확히 1장 |
| 단계 사진 | 단계당 최대 1장, 선택 |
| 팁 | 최대 2,000자, 선택 |
| 태그 | 최대 5개, 각 2~20자, 중복 제거 |
| 권리 확인 | 자신이 작성한 설명과 사용할 권한이 있는 이미지임을 확인 |
| 경제적 관계 | 제품 제공이나 광고 등 관계가 있으면 표시하도록 입력 제공 |

초안은 일부 누락을 허용하지만 자료형과 최대 크기는 검증한다. 발행 시 전체 검증을 한다. `expectedDraftVersion`으로 여러 탭의 편집 충돌을 감지하며 최신 내용을 무조건 덮어쓰지 않는다.

수정은 기존 발행 내용을 변경하는 것이 아니라 다음 버전 초안을 만든다. 공백이나 동일 내용만 바꾼 재발행은 막는다. 버전을 바꾸어도 과거 평점과 신고 이력이 사라지는 것은 아니다.

### 후기와 댓글

후기는 사진 1~3장, 정수 별점 1~5, 본문 20~2,000자다. 댓글과 답글은 1~1,000자다. 점수 선택기는 키보드 조작과 읽기 가능한 레이블을 제공한다.

후기 편집 시 월간 평가의 반영 상태를 보여 준다. 평가 마감 뒤 일반 후기 평점을 수정하더라도 해당 월의 평가 스냅샷은 바뀌지 않는다. 삭제나 신고로 집계 자격이 달라지는 예외는 어워즈 명세를 따른다.

### 어워즈와 명예의전당

접수, 평가, 검토, 결과 발표 상태를 날짜와 함께 표시한다. 행사에는 주제, 참가 자격, 일정, 최소 후기 수, 점수 산식, 동점 규칙, 부정 참여 처리, 이의 제기 경로가 있어야 한다.

평가 중 후보 목록은 점수순으로 기본 정렬하지 않는다. 날짜별로 재현 가능한 균등 노출 순서를 사용한다. 일반 상세 페이지의 평점은 공개되므로 이를 완전한 블라인드 심사라고 표현하지 않는다.

수상작이 없으면 `이번 달은 최소 평가 조건을 충족한 수상작이 없습니다`를 표시한다. 관리자가 임의로 부족한 자리를 채우지 않는다. 명예의전당은 확정된 결과만 노출한다.

### 프로필과 내 공간

공개 프로필은 닉네임, 소개, 아바타, 공개 레시피, 공개 후기, 확정 수상 기록으로 구성한다. 이메일, 로그인 정보, 비공개 저장 목록, 신고 기록은 공개하지 않는다. 닉네임은 표시 이름이며 handle은 URL 식별자다. handle 변경은 첫 베타에서 제한해 공유 링크가 끊기지 않게 한다.

### 관리자

신고함, 숨김 처리, 계정 제한, 행사 설정, 집계 미리보기, 결과 확정, 실패 작업 재시도를 우선 제공한다. 조회수가 많아 보이는 화려한 대시보드보다 실제 운영 동작을 우선한다. 삭제, 숨김, 실격, 결과 취소에는 사유와 확인 단계를 요구한다.

## 7. 디자인 방향

요리 사진이 중심인 따뜻한 에디토리얼 스타일을 기본안으로 한다. 과도한 게임 UI, 금색 효과, 트로피 애니메이션보다 읽기 쉬운 재료와 조리법을 우선한다.

| 토큰 | 기본안 |
|---|---|
| 배경 | 따뜻한 아이보리 `#FAF8F4` |
| 표면 | 흰색 `#FFFFFF` |
| 본문 | 짙은 중성색 `#252525` |
| 주 행동 | 깊은 테라코타 `#A8432B` |
| 보조 강조 | 짙은 녹색 `#2E5B46` |
| 본문 크기 | 모바일 기본 16px, line-height 1.6 이상 |
| 카드 모서리 | 12~16px, 약한 테두리 |
| 콘텐츠 폭 | 본문 최대 1,200px, 상세 읽기 영역은 더 좁게 |
| 간격 | 4px 기반 토큰 |

색 조합은 구현 후 대비를 측정해 조정한다. 수상 등급은 색뿐 아니라 `금상/은상/동상` 텍스트로 구분한다. 폰트는 시스템 한글 sans-serif로 시작해 외부 폰트 네트워크 의존성을 만들지 않는다.

필수 공통 컴포넌트는 AppHeader, MobileNav, RecipeCard, RecipeMeta, RatingSummary, StarRatingInput, IngredientList, StepList, RecipeEditor, ImageUploader, AwardBadge, CommentThread, EmptyState, ErrorState, ConfirmDialog, Pagination이다. 아직 한 곳에서만 쓰이는 작은 UI를 무조건 라이브러리로 추상화하지 않는다.

## 8. 상태와 접근성

모든 조회 화면은 로딩, 비어 있음, 실패, 정상 상태를 구현한다. 모든 변경 동작은 제출 중, 성공, 실패, 중복 클릭 방지 상태가 있다. 사용자가 수정 중인 내용을 오류 때문에 초기화하지 않는다.

360px 모바일부터 1,440px 데스크톱까지 확인한다. 터치 요소는 가능한 한 44px 이상으로 잡는다. 모달은 포커스 이동과 복귀, Escape 닫기, 스크롤 잠금을 처리한다. 이미지에는 용도에 맞는 대체 텍스트가 있어야 한다. 드래그 정렬을 구현하면 버튼 방식의 순서 이동도 제공한다.

## 9. 제품 성공 측정

첫 베타의 핵심 지표는 `게시물 수` 하나가 아니다. 주간 신규 발행자 수, 본인이 아닌 사용자의 후기를 받은 레시피 비율, 주간 고유 후기 작성자 수, 작성자의 4주 내 재발행, 행사 출품자와 실제 평가 참여자 수를 함께 본다.

첫 실험의 운영 목표 예시는 초대 작성자 10명, 공개 레시피 30개, 서로 다른 사용자의 요리 후기 20개다. 시장 기준이나 성공 보장 수치가 아니라 작은 모집 실험의 가정이다. 가짜 계정, 개발 seed, 운영자 테스트는 목표 달성에 포함하지 않는다.

## 10. 문서 간 기준
