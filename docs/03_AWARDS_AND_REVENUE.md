# 월간 어워즈와 수익화 명세

버전: 1.0 | 기준일: 2026-10-12

이 문서의 일정, 최소 평가 수, 보정값은 구현을 위한 기본안이다. 사용자와 실험 결과에 따라 **다음 행사부터** 변경할 수 있지만 이미 공개한 행사의 규칙을 소급 변경하지 않는다.

## 1. 일반 평점과 월간 평가를 분리한다

| 항목 | 일반 레시피 평점 | 월간 어워즈 |
|---|---|---|
| 목적 | 해당 조리법을 선택할 때 참고 | 특정 행사에서 수상자를 선정 |
| 대상 | 현재 공개 버전의 정상 요리 후기 | 출품 시 고정된 버전의 적격 평가 |
| 기간 | 누적 | 지정된 평가 시작 이상, 종료 미만 |
| 점수 표시 | 실제 별점 평균과 후기 수 | 실제 평균, 적격 후기 수, 보정 점수 |
| 댓글/북마크 | 점수에 미포함 | 점수에 미포함 |
| 마감 이후 수정 | 현재 평점에는 반영 가능 | 종료된 평가의 점수 스냅샷은 변경하지 않음 |
| 확정 결과 | 해당 없음 | 별도 결과 스냅샷을 보존 |

UI에서 `평균 4.8점`과 `어워즈 보정 점수 4.54`를 같은 값처럼 취급하지 않는다. 보정 점수를 검색 구조화 데이터의 aggregateRating에 넣지 않는다.

## 2. 행사 일정

### 기본 월간 일정

한국 시간 기준 매월 1일 00:00에 접수를 시작한다. 21일 00:00에 접수를 닫고 평가를 시작한다. 다음 달 1일 00:00에 평가를 닫는다. 운영 검토와 이의 접수 기간을 거쳐 다음 달 4일 00:00 이후에 결과를 확정할 수 있다.

**기간은 항상 `[시작, 종료)`의 반열린 구간이다.** 마감일 23:59:59를 계산해 저장하지 않는다. 캘린더 월을 사용하며 30일을 더하는 방식으로 다음 달을 계산하지 않는다.

| 예시: 2026년 11월 행사 | 한국 시간 | UTC 저장값 |
|---|---|---|
| 접수 시작 | 2026-11-01 00:00 +09:00 | 2026-10-31T15:00:00Z |
| 접수 마감 | 2026-11-21 00:00 +09:00 | 2026-11-20T15:00:00Z |
| 평가 시작 | 2026-11-21 00:00 +09:00 | 2026-11-20T15:00:00Z |
| 평가 종료 | 2026-12-01 00:00 +09:00 | 2026-11-30T15:00:00Z |
| 확정 가능 시각 | 2026-12-04 00:00 +09:00 | 2026-12-03T15:00:00Z |

위 날짜는 일정 구현을 위한 예시다. 실제 서비스가 11월에 시작된다는 의미가 아니다.

늦게 출품한 레시피도 같은 평가 기간을 받도록 접수와 평가를 분리한다. 접수 기간에 일반 후기가 달릴 수 있지만 그 후기는 월간 평가로 자동 소급 포함하지 않는다. 평가 기간 전에 이미 같은 버전에 후기를 쓴 사용자는 평점을 수정하는 것만으로 월간 평가자가 될 수 없다. 첫 베타의 단순하고 공개 가능한 규칙으로 선택한 제한이며, 나중에 별도 대회 평가를 도입할지는 실제 불편을 보고 결정한다.

### 상태 모델

DB의 state는 draft/published/finalized/cancelled다. published 행사 안의 현재 단계는 DB 시각으로 계산한다.

```text
DRAFT
  └─ 관리자 공개 → PUBLISHED
       ├─ 접수 시작 전: 예정
       ├─ 접수 시작 이상, 접수 마감 미만: 접수 중
       ├─ 평가 시작 이상, 평가 종료 미만: 평가 중
       └─ 평가 종료 이후: 검토 중
            └─ 관리자 확정 → FINALIZED

DRAFT 또는 PUBLISHED → 사유 있는 관리자 취소 → CANCELLED
```

일정만 지나면 출품과 평가 쓰기가 자동 차단되어야 한다. cron이 실행돼 상태 값을 바꿔야만 마감되는 구조는 금지한다. 첫 베타는 관리자 수동 공개와 확정으로 운영한다. 자동 작업을 추가하더라도 같은 DB 함수를 호출하고 중복 실행에 안전해야 한다.

## 3. 출품 규칙

첫 베타의 일반 어워즈에서는 한 작성자가 한 행사에 하나의 레시피만 출품한다. 한 레시피도 해당 행사에 한 번만 출품한다. 탈퇴나 철회 후 다른 계정으로 제한을 우회하는 문제는 별도 부정 참여 판단 대상이다.

같은 달의 취소되지 않은 일반 행사는 하나만 존재한다. month_key와 부분 UNIQUE 제약으로 중복 생성을 막는다.

출품 함수가 검사할 조건은 다음과 같다.

- 정상 상태이고 이메일 확인을 마친 일반 회원이다. 관리자와 개발 fixture는 제외한다.
- 현재 DB 시각이 접수 기간 안이다.
- 본인이 작성한 공개 레시피이며, 최초 공개 시각이 해당 접수 기간 안이다.
- 선택한 버전은 해당 레시피의 현재 공개 버전이며, 완성 사진과 필수 입력이 유효하다.
- 행사 주제와 콘텐츠 가이드에 맞는지 본인이 확인하고 규칙에 동의한다.
- 같은 행사에 이미 본인 또는 같은 레시피의 출품이 없다.

출품된 recipe_version_id는 바꿀 수 없다. 접수 중 철회했다가 다시 참여할 때도 기존 출품과 같은 버전을 복원한다. 다른 버전으로 바꾸려면 다음 행사에서 새 규칙에 맞게 참여한다. 버튼을 누르기 전에 이 제한을 보여 준다.

작성자는 별도로 최신 버전을 발행할 수 있다. 다만 행사 화면과 후기 작성 화면은 출품 버전을 계속 기준으로 하고 `최신 버전과 다를 수 있습니다`를 안내한다.

행사 주제 적합성을 키워드 하나로 자동 판정하지 않는다. 관리자는 주제 위반, 도용, 조작 등 사유를 기록하고 실격 처리할 수 있으나 점수를 직접 올리거나 내리지 않는다.

## 4. 월간 평가 자격

사진을 첨부한 일반 요리 후기가 아래 조건을 충족할 때 어워즈 평가를 함께 생성한다. 별점만 보내는 별도의 `투표 API`는 만들지 않는다.

| 조건 | 검사 |
|---|---|
| 작성 시각 | 후기 최초 created_at이 평가 구간 안 |
| 버전 | 후기 recipe_version_id가 출품 버전과 동일 |
| 평가자 | 레시피 작성자와 다름, 정상 일반 회원, 이메일 확인 완료 |
| 계정 경과 시간 | 최초 평가 시각 기준 가입 후 24시간 이상 |
| 증빙 형태 | 본인 소유의 ready 상태 요리 사진 1~3장 |
| 본문과 점수 | 후기 입력 규칙 준수, 정수 1~5점 |
| 중복 | 해당 출품에 평가자별 하나 |
| 상태 | 공개된 정상 후기와 유효한 출품 |

가입 후 24시간 미만이라도 일반 요리 후기는 작성할 수 있다. 다만 이 후기는 월간 점수에 반영되지 않는다고 제출 전에 안내한다. 24시간이 지났다는 이유로 자동 소급 평가하지 않는다. 계정 경과 시간은 부정 이용을 줄이기 위한 약한 장치일 뿐, 1인 1계정을 증명하지는 않는다.

같은 버전의 후기 사진을 다른 후기에서 그대로 재사용하는 것은 asset 참조 제약으로 제한한다. 동일 이미지 해시는 검토 단서일 뿐 무조건 조작 판정 기준은 아니다. 이미지를 조금 수정한 중복, 지인 담합, 다중 계정을 완벽히 검출할 수 있다고 주장하지 않는다.

작은 점수를 준 후기라는 이유로 작성자가 삭제하거나 집계에서 제외할 수 없다. 작성자는 신고만 할 수 있고, 관리자 조치는 운영 가이드의 사유와 증거에 근거해야 한다.

## 5. 평가 스냅샷

award_evaluations는 후기와 연결되어 있지만 후기 자체와는 별개의 월간 점수 기록이다.

평가 기간 안에 적격 후기가 생성되면 entry_id, reviewer_id, review_id, rating_snapshot, evaluated_at을 저장한다. 같은 후기의 점수 변경은 평가 종료 전까지만 rating_snapshot에 반영한다. 처음부터 평가 자격이 없었던 과거 후기를 편집해 적격 평가로 바꾸지 않는다.

평가 종료 뒤에는 일반 후기 점수와 본문을 편집할 수 있어도 rating_snapshot은 그대로다. 이 때문에 사용자가 마감 이후 낮은 점수를 높은 점수로 바꾸거나 반대로 바꾸어 수상을 움직일 수 없다.

### 종료 전후 예외 처리

| 사건 | 평가 종료 전 | 종료 후, 결과 확정 전 | 결과 확정 후 |
|---|---|---|---|
| 후기 점수 변경 | 적격 평가의 snapshot 갱신 | snapshot 유지 | 확정 결과 유지 |
| 후기 삭제 또는 사진 전부 제거 | 평가 withdrawn | 평가 withdrawn | 공개 후기는 제거, 과거 결과 자동 재계산 안 함 |
| 관리자 후기 숨김/조작 판정 | 평가 excluded | 평가 excluded와 감사 기록 | 필요 시 수상 취소 검토, 점수 직접 수정 금지 |
| 레시피 삭제/숨김, 출품 철회 | 후보 제외 | 후보 제외 | 수상 기록은 최소정보/비공개 또는 취소 처리 |
| 평가자 탈퇴/이용 제한 | 미확정 평가 제외 | 미확정 평가 제외 | 공개 정보 정리, 과거 결과 자동 재계산 안 함 |
| 잘못된 숨김 복구 | 조건 충족 시 복구 | 기존 frozen 점수의 자격만 사유 있게 복구 | 자동 재계산 안 함 |

eligibility는 included/withdrawn/excluded로 관리한다. 내부 조작 판단 근거는 비공개 audit에 두고 공개 UI에는 필요한 반영 상태만 제공한다. 종료 후에는 평가 점수를 바꾸지 않으며 자격 제외와 복구만 사유 있게 처리한다.

마감 이후 수정된 일반 후기 점수가 아니라 평가 기간에 저장된 마지막 적격 snapshot이 집계의 원천이다. 원본 후기 본문과 사진을 집계용 테이블에 복사하지 않는다.

## 6. 순위 산정

### 기본 규칙: monthly-v1

최소 적격 후기 수는 서로 다른 평가자 5명이다. 별점 5점 후기 하나만으로 수상하는 일을 방지하기 위해 평균을 보정한다.

```text
v = 적격 평가자 수
rating_sum = 적격 rating_snapshot의 합
R = rating_sum / v
C = 3.5    # 행사 시작 전에 고정한 기준 평균
m = 5      # 기준 평균에 부여한 가상의 후기 수

S = (v × R + m × C) / (v + m)
  = (rating_sum + 17.5) / (v + 5)
```

C와 m은 실제 사이트 통계나 과학적으로 보장된 최적값이 아니라 서비스 기본 파라미터다. 설명 가능한 초기 규칙으로 사용하고 검증 후 다음 행사부터 변경할 수 있다. 데이터가 쌓인 뒤 C를 계산형으로 바꾸더라도 행사 시작 시 확정해 스냅샷으로 보관한다.

| 적격 후기 수 | 실제 평균 | 보정 점수 | 수상 자격 |
|---:|---:|---:|---|
| 1 | 5.0 | 3.750000 | 없음 |
| 5 | 5.0 | 4.250000 | 있음 |
| 20 | 4.6 | 4.380000 | 있음 |
| 100 | 4.7 | 4.642857 | 있음 |

예시는 산식 확인용 계산이다. 예상 서비스 평가 분포가 아니다. 후기 0개는 순위에서 제외한다. 평점순 탐색도 같은 형태의 보정식을 사용할 수 있지만, 탐색의 결과를 월간 수상 결과로 재사용하지 않는다.

### 정렬과 공동수상

적격 후보를 보정 점수 내림차순, 적격 평가 수 내림차순, 5점 평가 수 내림차순으로 정렬한다. 비교용 계산은 PostgreSQL NUMERIC으로 하고 표시용 반올림 값을 정렬에 쓰지 않는다.

세 값이 모두 같으면 공동순위다. `RANK()`의 경쟁 순위, 즉 `1, 1, 3` 방식을 적용한다. rank=1은 금상, rank=2는 은상, rank=3은 동상이다. 순위가 건너뛰면 해당 등급을 비워 둔다. 공동수상 때문에 실제 수상작 수가 3개를 초과할 수 있다. 화면상 정렬 안정화용 ID는 추가할 수 있지만, ID를 순위 계산의 동점 해소 기준으로 넣으면 안 된다.

최소 조건을 만족하는 후보가 1개면 금상만 수여한다. 후보가 없으면 수상 없음으로 확정한다. 관리자가 후기를 추가하거나 기준을 내려 빈자리를 채우지 않는다.

## 7. 안전한 집계와 결과 확정

관리 화면의 단순 반복문으로 전체 후보를 읽고 개별 UPDATE하는 방식은 사용하지 않는다. 집계 준비와 확정을 분리하고 DB 트랜잭션으로 처리한다.

### 7.1 입력 변경 잠금

각 행사에는 source_revision이 있다. 해당 행사에 영향을 주는 출품, 평가 자격, 평가 점수의 변경은 행사 행을 잠근 뒤 같은 트랜잭션에서 source_revision을 증가시킨다.

여러 행사를 다루는 운영 조치는 행사 ID 순으로 잠가 교착 가능성을 줄인다. 후기 갱신, 관리자 숨김, 탈퇴, 출품 철회도 같은 잠금 규칙을 사용한다. 절차를 우회한 테이블 직접 쓰기는 허용하지 않는다.

잠금을 얻은 다음 실제 DB 현재 시각을 검사한다. PostgreSQL의 transaction 시작 시각을 돌려주는 시간 함수만 사용하면 마감 전에 시작해 마감 후 잠금을 얻은 쓰기가 잘못 허용될 수 있다. 명세상 시간 경계 검사는 `clock_timestamp()` 같은 실제 현재 시각 기준으로 수행한다. 정확한 API 동작은 설치된 PostgreSQL 공식 문서를 확인한다. 참고자료는 04 문서의 S19다.

### 7.2 prepare_award_run

관리자 권한과 평가 종료를 확인하고 행사 행을 잠근다. 현재 source_revision, rules, 적격 출품과 평가 스냅샷을 읽어 private.award_run_inputs에 최소 입력을 저장한다. 정규화한 입력과 규칙의 해시를 만든다.

모든 적격 후보의 통계를 계산하고 순위와 medal을 award_results에 prepared 상태의 run 소속으로 저장한다. 수상자가 없는 경우도 정상 run이다. 같은 idempotency_key의 재시도는 중복 run을 생성하지 않는다.

관리자 화면은 이 결과와 제외 사유를 검토용으로 보여 준다. 준비된 결과는 공개 API와 명예의전당에서 보이지 않는다.

### 7.3 finalize_award_run

관리자는 `확정 가능 시각`, 후보와 제외 결과, 규칙, 보고된 문제를 확인한 뒤 확정한다. 함수는 행사 행을 다시 잠그고 다음을 확인한다.

- 아직 finalized 또는 cancelled가 아니다.
- 검토 기간이 지났다.
- source_revision이 준비된 run과 같다.
- 준비된 결과와 입력의 무결성이 유지된다.

그 사이 후기 삭제나 운영 조치로 source_revision이 변했으면 CONFLICT를 반환한다. 점수를 조용히 다시 계산해 확정하지 말고 새 미리보기를 만들고 검토한다.

성공 시 period.final_run_id 설정, period.state=finalized, run.status=finalized, finalized_at 저장, 수상 알림과 감사 기록을 **한 트랜잭션**으로 완료한다. 같은 run을 다시 확정해도 같은 성공 결과를 반환하고 알림이나 수상 행을 중복 생성하지 않는다. 다른 run의 중복 확정은 차단한다.

### 7.4 확정 이후

확정 결과의 점수와 순위는 일상적인 후기 변화로 바뀌지 않는다. 새 순위는 새로운 달의 행사에서 생긴다. 레시피를 수정하거나 삭제했을 때 과거 어워즈 카드가 최신 버전으로 자동 대체되지 않는다.

도용이나 중대한 조작이 뒤늦게 확인되면 관리자는 사유를 남기고 수상을 revoked로 표시할 수 있다. 첫 베타에서는 차순위 자동 승격이나 전체 순위 재발표를 지원하지 않는다. 정정 집계 기능을 도입한다면 새 run과 정정 공지를 만들고 이전 결과를 덮어쓰지 않는 별도 설계가 필요하다.

## 8. 운영의 신뢰 장치

행사 규칙 전문과 버전, 일정, 보정 산식, 수상 조건을 참가 전에 볼 수 있게 한다. 실격과 취소는 사유를 기록한다. 공개 사유에는 개인정보나 내부 보안 신호를 담지 않는다.

조회, 북마크, 작성자 인지도, 팔로워 수, 상품 클릭, 후원 금액은 일반 월간 점수에 포함하지 않는다. 운영자는 상금이 없는 초기 베타부터 이 원칙을 지킨다.

후기 사진이 실제 조리를 완전히 보증한다거나 이 점수가 객관적인 맛을 증명한다고 홍보하지 않는다. `사진 후기 기반 커뮤니티 평가`라고 설명한다. 맛은 주관적이고 부정 참여 방지는 제한적인 신뢰 장치라는 점을 운영 규칙에 반영한다.

## 9. 수익 모델 도입 순서

P0~P5는 커뮤니티를 실제로 운영할 수 있게 만드는 단계다. P6의 수익 기능을 추가해도 핵심 무료 기능은 유지한다.

| 순서 | 수익 수단 | 개발 범위 | 활성화 전 조건 |
|---|---|---|---|
| P6-A | 제휴 상품 | 관리자 링크 등록, 고지, 외부 이동, 클릭 측정 | 실제 제휴 승인, 게시 방식과 약관 확인 |
| P6-B | 브랜드 후원 챌린지 | 별도 행사 페이지, 후원 표시, 참여와 결과 집계 | 실제 후원 계약과 운영 담당자 확보 |
| 후속 검토 | 일반 광고 | 광고 슬롯과 동의/정책 대응 | 유입과 UX 영향 검증 |
| 후속 검토 | 유료 편의 기능 | 식단 계획 등 별도 기획 필요 | 반복 사용과 지불 의사 확인 |
| 후속 검토 | 창작자 정산/밀키트 | 현재 설계 범위 밖 | 결제, 세금, 정산, 상품 책임 등 추가 설계 |

수익화가 검토됐다는 이유로 레시피 열람권, 유료 투표권, 수상 확률 증가 상품을 만들지 않는다. 일반 순위의 신뢰를 판매하지 않는다.

## 10. P6-A 제휴 상품

### 사용자 경험

레시피의 재료와 도구 설명 아래에 `관련 상품` 영역을 배치한다. 작성자가 입력한 재료 이름과 분량을 광고 상품명으로 대체하지 않는다. 상품 링크는 해당 재료를 구매하는 선택지일 뿐 레시피 성공에 필수인 특정 브랜드로 표시하지 않는다.

첫 버전은 플랫폼 관리자가 승인된 링크만 등록한다. 일반 작성자가 임의의 단축 링크나 추적 코드를 삽입해 수익을 분배하는 기능은 제공하지 않는다. 제휴 영역이 없는 레시피에도 빈 광고 박스를 노출하지 않는다.

제휴 고지는 접힌 더보기나 푸터에만 숨기지 않고 관련 영역에서 보이게 한다. 기본 문구 예시는 `이 영역에는 제휴 링크가 포함되어 있으며, 구매가 발생하면 운영자가 수수료를 받을 수 있습니다.`다. 실제 제휴사의 필수 문구와 현행 표시 기준을 확인해 교체한다. 이 예문을 법률 검토가 끝난 완성 문구라고 취급하지 않는다.

### 링크 처리

제휴사가 제공한 원본 URL로 바로 이동하는 것을 기본으로 한다. 제휴 약관에서 허용하는지 확인하기 전에는 `/go` 리다이렉트, 링크 축약, 임의 쿼리 추가, 자동 장바구니 담기를 구현하지 않는다.

URL은 https와 승인된 정확한 hostname 목록으로 검증한다. 문자열에 브랜드 이름이 포함됐다는 이유로 허용하지 않는다. 새 창을 쓰면 noopener를 적용하고 sponsored 관계를 표시한다. referrer 정책은 제휴사의 추적 요구와 보안 조건을 확인한다.

재료 가격과 재고 API 연동은 첫 제휴 단계에 포함하지 않는다. 확인하지 않은 최신 가격, 최저가, 할인율을 표시하지 않는다.

### 데이터

```text
affiliate_links
  id, recipe_id, provider, label, original_url, disclosure_text,
  is_active, position, last_checked_at, created_by, created_at

private.affiliate_clicks
  event_id, link_id, recipe_id, occurred_at
```

event_id는 중복 전송을 줄이는 키다. 클릭 기록에는 기본적으로 사용자 이메일, 프로필 ID, 원문 IP, 전체 User-Agent를 넣지 않는다. 그래도 측정과 네트워크 로그의 개인정보 처리 여부는 운영 환경에서 검토한다.

클릭 수집 실패 때문에 외부 상품 이동을 막지 않는다. 클릭 이벤트는 구매와 같지 않으며 봇과 중복이 포함될 수 있다. 제휴사의 승인된 실적 자료가 없는 상태에서 클릭 수에 가정 전환율을 곱한 값을 `매출`로 기록하지 않는다.

## 11. P6-B 브랜드 후원 챌린지

후원 행사는 `/challenges/[slug]`에서 운영하고 일반 월간 행사와 구분한다. award_periods.kind=sponsored로 생성하며 일반 명예의전당 조회는 kind=monthly로 제한한다. 프로필 배지도 `일반 월간 금상`과 `브랜드 챌린지 수상`을 구별한다.

추가 테이블 sponsor_campaigns에는 period_id, sponsor_name, sponsor_logo_asset_id, product_description, disclosure_text, participation_terms, status를 둔다. 계약금, 담당자 연락처, 내부 성과 보고는 공개 필드와 분리한다.

브랜드가 얻는 것은 표시된 행사 공간과 참여 운영, 합의한 범위의 성과 자료다. 사용자의 사진과 설명을 외부 광고에 재사용하려면 게시물 공유 기능과 별개의 권리 허락 절차가 필요하다. 기본 가입만으로 무제한 상업적 이용을 승인했다고 가정하지 않는다.

첫 후원 챌린지는 일반 행사와 같은 설명 가능한 후기 기반 집계를 재사용한다. 별도 심사위원 평가, 상금 자동 송금, 경품 추첨, 기업 전용 계정은 자동 추가하지 않는다. 보상과 제품 제공이 있다면 행사 공개 전에 조건을 확정한다.

동일 레시피는 겹치는 기간의 일반 행사와 후원 행사에 동시에 출품하지 못하게 한다. 후기 하나가 두 행사에 자동 중복 반영되지 않도록 P6에서 참여 맥락과 중복 제약을 검증한다. 후원 행사에 모인 평가를 일반 어워즈 평가 테이블에 복사하지 않는다.

## 12. 수익과 사업 지표

관리자가 볼 지표는 제휴 링크별 노출/클릭을 구분할 수 있을 때의 클릭률, 파트너가 확인한 구매 실적, 확정된 수수료, 후원 계약 매출, 캠페인 직접비, 운영비다. 측정하지 않은 분모로 클릭률을 만들지 않는다. 첫 클릭 버전에서 노출을 수집하지 않는다면 클릭 수만 표시한다.

예상값을 검토할 때 사용하는 산식은 다음과 같다.

```text
제휴 추정 수익 = 페이지 조회수 × 링크 클릭률 × 구매전환율 × 주문금액 × 수수료율
일반 광고 추정 수익 = 페이지 조회수 / 1,000 × 페이지 RPM
후원 직접 기여 = 후원 계약 매출 - 행사별 직접 비용
운영 손익 검토 = 실제 매출 - 직접 비용 - 인프라 비용 - 운영 인건비 등
```

이 산식의 각 입력은 실측이나 명시적 가정이어야 한다. 특정 제휴사의 현재 요율이나 광고 단가를 이 문서에서 확정하지 않는다. 예를 들어 10만 조회, 클릭률 3%, 구매전환율 3%, 주문 3만원, 수수료율 3%를 **가정하면** 제휴 추정 수익은 81,000원이다. 실제 매출 예상이나 시장 평균은 아니다.

수익 기능을 도입할지는 사용자 수 한 가지가 아니라 반복 레시피 등록, 실제 후기 발생, 운영자의 신고 처리 부담, 파트너 확보 여부로 판단한다. 실제 후원사가 없는 샘플 캠페인을 계약 실적으로 표시하지 않는다.

## 13. 우선 구현할 검증 사례

점수 5.0의 후기 1개 후보는 수상 불가여야 한다. 후기가 없는 달도 오류 없이 수상 없음으로 확정되어야 한다. 동일 점수 공동수상, 2월과 윤년, 연말 경계, 마감 직전 시작했으나 마감 후 잠금 획득한 쓰기, 미리보기 뒤 후기 삭제, 관리자 두 명의 동시 확정, 확정 후 후기 수정, 탈퇴자의 이미지 비노출을 자동 테스트한다.

수익화 단계에서는 기능 플래그가 꺼져 있을 때 제휴 영역과 이벤트 수집이 모두 비활성화되는지, 승인되지 않은 도메인이 차단되는지, 후원 점수가 일반 월간 결과에 섞이지 않는지 추가로 검증한다.
